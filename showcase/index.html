Decisiones que resolvieron los riesgos

El porqué detrás del modelo y las métricas.

01

Evitar importes duplicados

Riesgo: un pedido puede tener varios artículos y pagos; unir ambas tablas fila a fila multiplica valores. Solución: agregarlas por order_id antes de construir mart_order.

02

Definir “ingresos” con honestidad

Riesgo: los pagos incluyen estados cancelados y no hay libro fiable de reembolsos. Solución: usar precio de artículos entregados como proxy de valor, sin flete; exponer diferencias de pago.

03

Medir recompra por persona

Riesgo: customer_id identifica una compra, no necesariamente a la persona. Solución: agrupar pedidos entregados por customer_unique_id y calcular el denominador explícito.

04

Acotar las respuestas de GPT

Riesgo: SQL libre o cifras inventadas. Solución: GPT elige métrica y mes; la aplicación valida ambos, ejecuta SQL fijo de solo lectura y arma la respuesta desde el resultado.

05

Comparar entregas por fecha

Riesgo: la fecha prometida está a medianoche; comparar horas marcaría tarde una entrega realizada el mismo día. Solución: comparar las fechas calendario real y estimada.

06

Mostrar las excepciones

Riesgo: forzar pagos e importes a coincidir ocultaría diferencias reales. Solución: reconciliar por pedido y publicar 303 casos con diferencia mayor a R$ 0,01 para inspección.

Guion para presentarlo

Cómo explicar el enfoque en un minuto

1. El problema

Los CSV operativos no tienen una métrica única lista para negocio: mezclan granos, estados de pedido y pagos.

2. La solución

Ingerí la fuente, modelé hechos y dimensiones, construí marts con definiciones explícitas y validé cada paso.

3. El resultado

El tablero y la API responden las cinco preguntas. GPT solo interpreta la intención; los números vienen del modelo curado.

Límite que conviene mencionar: es una foto histórica Olist, no información actual de NearShift ni ingresos contables auditados.
